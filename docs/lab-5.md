# Лаба 5. Docker и запуск одной командой

**Цель:** проект поднимается на любой машине одной командой.

Срок: PR `lab-5 → main` до 23:59 накануне встречи 6. **Проверку соседом** нужно сделать до дедлайна.

## Что сделать

1. `Dockerfile` для бэкенда (и для фронта, если он отдельный).
2. `docker-compose.yml` (или `compose.yaml`): бэкенд + БД (+ фронт). Всё поднимается командой `docker compose up`.
3. Данные БД — в именованном volume.
4. Конфигурация — через `.env`; в репо лежит `.env.example`, с которым проект запускается как есть.
5. Каждый запрос пишет строку лога в stdout: метод, путь, статус, время.
6. Подключить workflow проверки (ниже) и попросить соседа поднять проект по README.

### Workflow проверки

Создай файл `.github/workflows/backcheck.yml` — ровно такой, менять ничего не нужно:

```yaml
name: backcheck
on:
  pull_request:
  workflow_dispatch:
jobs:
  backcheck:
    uses: bozhedom/backcheck/.github/workflows/lab5.yml@v1
```

На каждом PR GitHub на чистой машине выполнит `cp .env.example .env`, `docker compose up --build --wait` и прогонит чекер по базам лаб 1–5. Если галочка красная — открой лог: там тот же вывод, что у `backcheck` локально.

### Проверка соседом

Преподаватель распределит пары. Сосед клонирует твой репозиторий и поднимает проект **строго по README**, ничего не спрашивая. Потом пишет в твоём PR комментарий:

> Поднял по README за 4 минуты, коммит abc1234. Всё работает.

или список того, что пришлось сделать сверх README. Ссылку на комментарий вставь в чек-лист PR.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | Dockerfile для бэкенда | Dockerfile есть, `.env` не копируется в образ, в compose есть `build:`. ⚠ если код копируется раньше зависимостей |
| 2 | `docker compose up` поднимает бэкенд + БД (+ фронт) | Все сервисы из compose запущены, `/health` → 200, фронт отвечает |
| 3 | Чужая машина: клонирует и запускает по README за 5 минут | Зелёный workflow + комментарий соседа в PR (преподаватель выборочно повторяет у себя) |
| 4 | Данные в volume: после `down` и `up` записи на месте | Чекер создаёт запись, сам делает `docker compose down` и `up`, проверяет запись |
| 5 | Конфигурация через `.env`, `.env.example` есть, секретов в git нет | `.env` не в git; в compose нет паролей открытым текстом (только `${...}` или `env_file`). ⚠ если `.env` когда-то был в истории git |
| 6 | Каждый запрос пишет строку лога, видно в `docker compose logs` | Чекер шлёт запрос с меткой и находит его строку в логах сервиса: статус и время на месте |

## ★ (2 балла): CI с автотестами

- Свой workflow в GitHub Actions: сборка + минимум 3 автотеста API — создание, 404, 401.
- Зелёная галочка на PR.

Workflow `backcheck.yml` — проверка преподавателя, за ★ он не считается. 2 балла — зелёный свой CI и 3 настоящих теста API; 1 — CI есть, но тестов меньше или они не ходят в API.

## ★★ (2 балла): одно на выбор

- **(а) Публичный деплой:** проект открывается по ссылке из интернета (VPS, Render, Railway, Fly.io…). Преподаватель откроет ссылку с телефона через мобильный интернет. Туннель с ноутбука (ngrok) — только 1 балл.
- **(б) Второй сервис** на Go или другом языке, не основном, в отдельном контейнере. Основной сервис ходит в него по HTTP (отчёт, уведомления, расчёт фишки) и, если второй сервис недоступен, отвечает 502/503, а не падает.

## contract.json: что добавить

```json
{
  "compose_service": "backend",
  "public_url": "https://my-project.example.com",
  "second_service": {
    "name": "reports",
    "trigger": { "method": "POST", "path": "/api/habits/{id}/checks", "body": { "date": "2026-10-01" } },
    "expect_when_down": [502, 503, 504]
  }
}
```

`compose_service` — имя сервиса бэкенда в compose. `public_url` — для варианта (а), `second_service` — для (б): `trigger` — запрос к основному сервису, во время которого он ходит во второй.

## Проверь себя

```bash
git clone <свой репозиторий> /tmp/check && cd /tmp/check   # как будто ты сосед
cp .env.example .env
docker compose up -d --build
backcheck --lab 5 --stars
backcheck --lab 5 --all --ci        # то же, что сделает GitHub Actions
```

## Сценарий демонстрации на паре

`git clone` → `cp .env.example .env` → `docker compose up` → открыть фронт → создать запись → `down` → `up` → запись на месте → `logs`.

## Подсказки

- Внутри сети compose к БД обращаются по **имени сервиса**: `postgres://user:pass@db:5432/app`, а не `localhost`.
- Бэкенд стартует раньше БД → `depends_on: db: condition: service_healthy` + `healthcheck` у БД.
- Сначала `COPY` файлов зависимостей и их установка, потом `COPY` кода — тогда правка кода не переустанавливает зависимости.
- Сервер внутри контейнера должен слушать `0.0.0.0`, а не `127.0.0.1`.
- `docker compose down -v` удаляет volume вместе с данными — на демо так не делай.
