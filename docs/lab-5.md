# Лаба 5. Docker и запуск одной командой

**Цель:** проект поднимается на любой машине одной командой `docker compose up`.

Срок: PR из `lab-5` в `main` до 23:59 накануне встречи 6. **Проверка на чужой машине** тоже делается до дедлайна.

## Что сделать

1. `Dockerfile` для бэкенда (и для фронтенда, если он отдельный).
2. `docker-compose.yml` или `compose.yaml`: бэкенд, база данных и фронтенд. Всё поднимается командой `docker compose up`.
3. Данные базы лежат в именованном volume, чтобы не пропадать при пересоздании контейнера.
4. Настройки берутся из `.env`. В репозитории лежит `.env.example`, с которым проект запускается без правок.
5. Каждый запрос пишет строку лога в stdout: метод, путь, статус, время.
6. Подключить workflow проверки (ниже) и попросить одногруппника поднять проект по README.

### Workflow проверки

Нужно создать файл `.github/workflows/backcheck.yml` ровно с таким содержимым:

```yaml
name: backcheck
on:
  pull_request:
  workflow_dispatch:
jobs:
  backcheck:
    uses: bozhedom/backcheck/.github/workflows/lab5.yml@v1
```

На каждом PR GitHub на чистой машине выполнит `cp .env.example .env`, `docker compose up --build --wait` и прогонит чекер по базам лаб 1-5. Если галочка красная, в логе будет тот же вывод, что у `backcheck` локально.

### Проверка на чужой машине

Одногруппник клонирует репозиторий и поднимает проект **строго по README**, ничего не спрашивая. Потом пишет в PR комментарий, например:

> Поднял по README за 4 минуты, коммит abc1234. Всё работает.

Или перечисляет, что пришлось сделать сверх README. Ссылка на комментарий вставляется в чек-лист PR.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | Dockerfile для бэкенда | Dockerfile есть, `.env` не копируется в образ, в compose есть `build:`. Предупреждение, если код копируется раньше зависимостей |
| 2 | `docker compose up` поднимает бэкенд, базу и фронтенд | Все сервисы из compose запущены, `/health` отвечает 200, фронтенд отвечает |
| 3 | Проект запускается на чужой машине по README за 5 минут | Зелёный workflow и комментарий одногруппника в PR. Выборочно запуск повторяется на приёме |
| 4 | Данные в volume: после `down` и `up` записи на месте | Чекер создаёт запись, сам делает `docker compose down` и `up` и проверяет запись |
| 5 | Настройки через `.env`, `.env.example` есть, секретов в git нет | `.env` не в git; в compose нет паролей открытым текстом (только `${...}` или `env_file`). Предупреждение, если `.env` когда-то был в истории git |
| 6 | Каждый запрос пишет строку лога, её видно в `docker compose logs` | Чекер отправляет запрос с меткой и находит его строку в логах: статус и время на месте |

## ★ (2 балла): CI с автотестами

- Свой workflow в GitHub Actions: сборка и минимум 3 автотеста API (создание, 404, 401).
- Зелёная галочка на PR.

Workflow `backcheck.yml` за ★ не считается, это общая проверка курса. 2 балла: свой CI зелёный и в нём 3 настоящих теста API. 1 балл: CI есть, но тестов меньше или они не обращаются к API.

## ★★ (2 балла): одно на выбор

- **(а) Публичный деплой:** проект открывается по ссылке из интернета (VPS, Render, Railway, Fly.io и подобные). Ссылку открывают с телефона через мобильный интернет. Туннель с ноутбука (ngrok) даёт только 1 балл.
- **(б) Второй сервис** на Go или другом языке, не основном, в отдельном контейнере. Основной сервис обращается к нему по HTTP (отчёт, уведомления, расчёт фишки), а если второй сервис недоступен, отвечает 502 или 503, а не падает.

## contract.json: что добавить

```json
{
  "compose_service": "backend",
  "public_url": "https://my-project.example.com",
  "second_service": {
    "name": "reports",
    "trigger": { "method": "POST", "path": "/api/books/{id}/loans", "body": { "reader": "Иванов", "taken_at": "2026-10-01" } },
    "expect_when_down": [502, 503, 504]
  }
}
```

`compose_service` это имя сервиса бэкенда в compose. `public_url` нужен для варианта (а), `second_service` для варианта (б). В `trigger` указывается запрос к основному сервису, во время которого он обращается ко второму.

## Как проверить себя

```bash
git clone <свой репозиторий> /tmp/check && cd /tmp/check   # как будто это чужая машина
cp .env.example .env
docker compose up -d --build
backcheck --lab 5 --stars
backcheck --lab 5 --all --ci        # то же, что сделает GitHub Actions
```

## Сценарий демонстрации на паре

`git clone`, `cp .env.example .env`, `docker compose up`, открыть фронтенд, создать запись, `docker compose down`, `docker compose up`, запись на месте, `docker compose logs`.

## Подсказки

- Внутри сети compose к базе обращаются по **имени сервиса**: `postgres://user:pass@db:5432/app`, а не `localhost`.
- Если бэкенд стартует раньше базы: `depends_on` с `condition: service_healthy` и `healthcheck` у базы.
- Сначала копируются файлы зависимостей и ставятся зависимости, потом копируется код. Тогда правка кода не переустанавливает зависимости заново.
- Сервер внутри контейнера должен слушать `0.0.0.0`, а не `127.0.0.1`.
- `docker compose down -v` удаляет volume вместе с данными. На демонстрации так делать не нужно.

4. Как контейнеры находят друг друга в compose?
5. Почему из контейнера бэкенда нельзя обратиться к базе по `localhost`?
6. Что такое слои образа и почему зависимости копируются раньше кода?
7. Что такое CI и что проверяет пайплайн проекта?
8. Что делать, если бэкенд стартует раньше базы?

Возможные живые правки: поменять внешний порт; добавить переменную окружения и вывести её в `/health`; добавить в compose Adminer или pgAdmin.
