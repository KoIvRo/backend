# Лаба 5. Docker и соседние сервисы

**Цель:** проект поднимается на любой машине одной командой `docker compose up`, а рядом с основным сервисом работает второй, и они общаются по сети. Это первый шаг к микросервисам. Звёздочки добавляют то, что стоит почти в любом рабочем бэкенде: CI, прокси, кэш, очередь, деплой.

Срок: PR из `lab-5` в `main` до 23:59 накануне встречи 6.

## Что сделать

1. `Dockerfile` для бэкенда (и для страницы, если она отдельная).
2. `compose.yaml`: бэкенд, база данных, второй сервис и страница. Всё поднимается командой `docker compose up`.
3. Данные базы лежат в именованном volume, чтобы не пропадать при пересоздании контейнера.
4. Настройки берутся из `.env`. В репозитории лежит `.env.example`, с которым проект запускается без правок.
5. **Второй сервис** в отдельном контейнере, лучше на другом языке. Основной сервис обращается к нему по HTTP по имени сервиса, например `http://reports:8080`. Если второй сервис недоступен, основной отвечает **503** с понятным текстом, а не падает и не отвечает 500.
6. Каждый запрос пишет строку лога в stdout: метод, путь, статус, время.
7. Подключить workflow проверки (ниже).

### Каким может быть второй сервис

Маленький сервис на 50-100 строк с одним эндпоинтом, который основной сервис вызывает в нужный момент:

| Тема | Второй сервис |
| --- | --- |
| Кинотеатр | Расчёт цены билета: дата, время сеанса, скидки |
| Учёт расходов | Конвертация валют |
| Бронирование отеля | Проверка, свободны ли даты |
| Блог, форум | Проверка текста на запрещённые слова |
| Любая | Генерация отчёта в CSV по данным, которые прислал основной сервис |

### Workflow проверки

Нужно создать файл `.github/workflows/backcheck.yml` ровно с таким содержимым:

```yaml
name: backcheck
on:
  pull_request:
  workflow_dispatch:
jobs:
  backcheck:
    uses: bozhedom/backcheck/.github/workflows/lab5.yml@v1
```

На каждом PR GitHub на чистой машине выполнит `cp .env.example .env`, `docker compose up --build --wait` и прогонит чекер по базам лаб 1-5. Если галочка красная, в логе будет тот же вывод, что у `backcheck` локально.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | Dockerfile для бэкенда | Dockerfile есть, `.env` не копируется в образ, в compose есть `build:`. Предупреждение, если код копируется раньше зависимостей |
| 2 | `docker compose up` поднимает всё, проверка на чистой машине зелёная | Все сервисы из compose запущены, `/health` отвечает 200, страница отвечает; `backcheck.yml` подключён, галочка на PR зелёная |
| 3 | Данные в volume: после `down` и `up` записи на месте | Чекер создаёт запись, сам делает `docker compose down` и `up` и проверяет запись |
| 4 | Настройки через `.env`, `.env.example` есть, секретов в git нет | `.env` не в git; в compose нет паролей открытым текстом (только `${...}` или `env_file`). Предупреждение, если `.env` когда-то был в истории git |
| 5 | Второй сервис: основной ходит в него по HTTP, при его остановке отвечает 503 | Чекер выполняет `trigger`, затем `docker compose stop` второго сервиса, повторяет `trigger` и ждёт 502, 503 или 504 |
| 6 | Каждый запрос пишет строку лога, её видно в `docker compose logs` | Чекер отправляет запрос с меткой и находит его строку в логах: статус и время на месте |

## ★ (2 балла): CI и прокси

Две части, каждая даёт 1 балл.

- **CI с автотестами.** Свой workflow в GitHub Actions: сборка и минимум 3 автотеста API (создание, 404, 401), зелёная галочка на PR. Workflow `backcheck.yml` сюда не считается, это общая проверка курса.
- **Nginx как единая точка входа.** В compose стоит Nginx (или Caddy, Traefik). Он отдаёт страницу и передаёт запросы `/api` бэкенду. Снаружи один адрес, например `http://localhost:8080`: на `/` страница, на `/api/...` и `/health` ответы бэкенда.

Пример `nginx.conf`:

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    location / { try_files $uri $uri/ /index.html; }
    location ~ ^/(api/|auth/|health$) {
        proxy_pass http://backend:8000;
        proxy_set_header Host $host;
    }
}
```

## ★★ (2 балла): кэш, брокер, деплой, любые два из трёх

Две части из трёх дают 2 балла, одна даёт 1.

- **Кэш в Redis.** Redis в compose. Ответ статистики (или другого тяжёлого запроса) кладётся в Redis на минуту. В ответе заголовок `X-Cache: MISS`, если посчитано в базе, и `X-Cache: HIT`, если взято из кэша. После создания или изменения записей кэш сбрасывается, и устаревшие цифры не отдаются.
- **Событие через брокер сообщений.** RabbitMQ (или Redis, Kafka, NATS) в compose. После действия в основном сервисе (новая бронь, новый отзыв) в очередь уходит событие, а отдельный сервис-получатель его читает и пишет строку в лог, например «письмо пользователю: бронь 15 подтверждена». Основной сервис не ждёт получателя: если получатель остановлен, запрос всё равно проходит, а событие дожидается его в очереди.
- **Публичный деплой с HTTPS.** Проект открывается по ссылке из интернета по `https://` (VPS, Render, Railway, Fly.io, Yandex Cloud и подобные). Ссылку открывают с телефона через мобильный интернет. Туннель с ноутбука (ngrok) не подходит.

## contract.json: что добавить

```json
{
  "compose_service": "backend",
  "second_service": {
    "name": "reports",
    "trigger": { "method": "POST", "path": "/api/books/{id}/loans", "body": { "reader": "Иванов", "taken_at": "2026-10-01" } },
    "expect_when_down": [502, 503, 504]
  },
  "proxy_url": "http://localhost:8080",
  "cache": { "path": "/api/books/stats", "header": "X-Cache" },
  "broker": {
    "consumer": "notifier",
    "trigger": { "method": "POST", "path": "/api/books/{id}/loans", "body": { "reader": "bc-{tag}", "taken_at": "2026-10-01" } }
  },
  "public_url": null
}
```

| Поле | Что писать |
| --- | --- |
| `compose_service` | Имя сервиса бэкенда в compose |
| `second_service.name` | Имя второго сервиса в compose |
| `second_service.trigger` | Запрос к основному сервису, во время которого он обращается ко второму. `{id}` заменяется на id новой записи, которую создаст чекер |
| `proxy_url` | Только для ★: адрес прокси |
| `cache` | Только для ★★: адрес, ответ которого кэшируется, и имя заголовка |
| `broker.consumer` | Только для ★★: имя сервиса-получателя в compose |
| `broker.trigger` | Только для ★★: запрос, после которого уходит событие. Вместо `{tag}` чекер подставит метку, она должна попасть в строку лога получателя |
| `public_url` | Только для ★★: публичный адрес с `https://` |

## Как проверить себя

```bash
git clone <свой репозиторий> /tmp/check && cd /tmp/check   # как будто это чужая машина
cp .env.example .env
docker compose up -d --build
backcheck --lab 5 --stars
backcheck --lab 5 --all --ci        # то же, что сделает GitHub Actions
```

## Сценарий демонстрации на паре

`git clone`, `cp .env.example .env`, `docker compose up`, открыть страницу, создать запись, `docker compose down`, `docker compose up`, запись на месте, `docker compose stop` второго сервиса и запрос, который даёт 503, `docker compose logs`.

## Подсказки

- Внутри сети compose к базе и другим сервисам обращаются по **имени сервиса**: `postgres://user:pass@db:5432/app`, `http://reports:8080`, `redis://redis:6379`, а не `localhost`.
- Если бэкенд стартует раньше базы: `depends_on` с `condition: service_healthy` и `healthcheck` у базы.
- Сначала копируются файлы зависимостей и ставятся зависимости, потом копируется код. Тогда правка кода не переустанавливает зависимости заново.
- Сервер внутри контейнера должен слушать `0.0.0.0`, а не `127.0.0.1`.
- `docker compose down -v` удаляет volume вместе с данными. На демонстрации так делать не нужно.
- Обращение ко второму сервису делается с таймаутом в 1-2 секунды. Без таймаута основной сервис будет ждать ответа бесконечно.
- Готовые образы: `redis:7-alpine`, `rabbitmq:4-management-alpine` (панель на порту 15672), `nginx:1.27-alpine`.
- Библиотеки для RabbitMQ: `pika` (Python), `amqplib` (Node.js), `github.com/rabbitmq/amqp091-go` (Go), Spring AMQP (Java), `RabbitMQ.Client` (C#), `php-amqplib` (PHP).
