# Лаба 4. Веб-страница и безопасность в браузере

**Цель:** у проекта появляется страница в браузере, которая работает с настоящим API, и защита от атак, которые идут через браузер: XSS и CSRF. Подойдёт чистый HTML и JavaScript, подойдёт и фреймворк. Страницу можно писать с помощью ИИ, но на приёме спрашивают про связь с сервером: какие запросы уходят, что приходит, как обрабатываются ошибки и почему страница не уязвима.

Срок: PR из `lab-4` в `main` до 23:59 накануне встречи 5.

## Что сделать

1. Страница со списком записей из API, формой входа, созданием и удалением.
2. Ошибки API (400, 401, 404) показываются на странице понятным текстом.
3. Текст из базы выводится как текст: `textContent` или шаблон фреймворка, а не `innerHTML`. Запись с названием `<img src=x onerror=alert(1)>` показывается буквами, и окно не всплывает.
4. Если страница и бэкенд на разных портах, на бэкенде настраивается CORS. Если страницу отдаёт сам бэкенд, CORS не нужен, и на приёме нужно объяснить почему.
5. Скриншот интерфейса добавляется в README.

Самый простой вариант без сборки: папка `frontend/` с файлами `index.html` и `app.js`, запуск командой `python -m http.server 5173` из этой папки.

## Чек-лист базы (6 баллов) и как его проверяют

Часть пунктов проверяется вручную. Чекер ведёт по сценарию и проверяет то, что видно по HTTP.

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | Страница открывается и загружает список с API, это видно во вкладке Network | Чекер: `frontend_url` отдаёт HTML, через API создаётся запись с меткой `backcheck-XXXX`. Вручную: после обновления страницы метка видна, в Network есть запрос к API |
| 2 | Форма входа: без входа изменять нельзя (кнопок нет или понятная ошибка) | Вручную, в режиме инкогнито |
| 3 | Создание и удаление через интерфейс | Вручную: новая запись появляется в списке без ручного обновления страницы, в Network виден `POST` с ответом 201. Метку чекера удаляют кнопкой, чекер проверяет, что на сервере её нет (`GET` даёт 404) |
| 4 | Ошибки 400, 401, 404 показываются понятным текстом | Вручную: пустое поле, неверный пароль, удалённая запись |
| 5 | XSS: опасная строка показывается текстом | Чекер создаёт запись с `<img src=x onerror=alert('backcheck')>`, вручную: строка видна на странице, окно не всплыло |
| 6 | CORS настроен, или страницу отдаёт сам бэкенд | Чекер отправляет preflight `OPTIONS` с `Origin` страницы: нужен 2xx, `Access-Control-Allow-Origin` и разрешённый заголовок `Authorization` |

## ★ (2 балла): редактирование, связанная сущность, заголовки безопасности

Три части. Все три дают 2 балла, две дают 1.

- Редактирование записи через интерфейс.
- Страница записи со списком связанных записей и формой добавления.
- Заголовки безопасности. Ответы API содержат `X-Content-Type-Options: nosniff`. У страницы есть `Content-Security-Policy`: заголовком или тегом `<meta http-equiv="Content-Security-Policy">`. Политика разрешает скрипты только со своего адреса, без `'unsafe-inline'` в `script-src`.

Пример политики для страницы на `localhost:5173` и API на `localhost:8000`:

```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; connect-src 'self' http://localhost:8000; object-src 'none'">
```

## ★★ (2 балла): вход через cookie или обновления в реальном времени

Один из двух вариантов.

**(а) Вход через cookie и защита от CSRF.** `POST /auth/session` с логином и паролем ставит cookie с флагами `HttpOnly` и `SameSite=Lax` (или `Strict`), токена в `localStorage` нет. Изменяющие запросы с этой cookie требуют защиты от CSRF: заголовок `X-CSRF-Token`, который страница берёт из отдельной cookie или из ответа входа, или проверка заголовка `Origin`. Запрос с cookie, но с чужого сайта и без токена, получает 403.

**(б) Обновления в реальном времени.** Страница открыта в двух окнах. Запись, созданная в одном окне, появляется во втором сама, без F5. Сервер сообщает о новых данных через Server-Sent Events (`GET /api/events`, ответ `text/event-stream`) или WebSocket.

Чекер: для (а) проверяет флаги cookie, вход по ней и отказ запросу с чужого `Origin`. Для (б) с SSE открывает поток, создаёт запись и ждёт событие в потоке. WebSocket проверяется вручную.

## contract.json: что добавить

```json
{
  "frontend_url": "http://localhost:5173",
  "cookie": { "login_path": "/auth/session" },
  "realtime": { "type": "sse", "path": "/api/events" }
}
```

`cookie` нужен только для варианта (а), `realtime` только для (б), второй можно не писать. Для WebSocket пишется `"type": "websocket"`.

Открыть страницу, показать вкладку Network, войти, создать запись, получить ошибку на пустом поле, удалить запись, показать запись с `<img src=x onerror=alert(1)>` в списке, выйти.

## Подсказки

- Запрос из JavaScript: `fetch(url, { method: "POST", headers: { "Content-Type": "application/json", Authorization: ... }, body: JSON.stringify(data) })`.
- `response.ok` равен `false` для ответов 4xx и 5xx. Сам `fetch` выбрасывает исключение, только если сервер вообще не ответил.
- Текст из API вставляется через `element.textContent = ...`. `innerHTML` с данными из API и есть XSS. В React, Vue и Svelte шаблоны экранируют текст сами, опасны только `dangerouslySetInnerHTML`, `v-html` и `{@html}`.
- CORS: в FastAPI это `CORSMiddleware`, в Express пакет `cors`, в Go заголовки `Access-Control-Allow-*` и ответ на `OPTIONS`, в Spring `@CrossOrigin` или `CorsConfigurationSource`, в ASP.NET `builder.Services.AddCors`.
- `localhost:5173` и `127.0.0.1:5173` для браузера **разные** origin.
- Cookie с другого порта: для `fetch` нужен `credentials: "include"`, а на сервере `Access-Control-Allow-Credentials: true` и точный origin вместо `*`.
- SSE на странице: `const events = new EventSource(API + "/api/events"); events.onmessage = () => load();`. На сервере ответ с `Content-Type: text/event-stream`, который не закрывается, и строки вида `data: {...}` с пустой строкой после каждой.
- Если страницу генерирует ИИ, ему стоит дать OpenAPI-описание своего API (`/openapi.json`), а потом проверить в Network каждый запрос.

## Вопросы, которые могут задать на приёме

1. Что происходит между нажатием кнопки и появлением записи в списке? Какие запросы уходят?
2. Что такое origin? Что такое CORS и кто его проверяет: браузер или сервер? Почему curl работает без CORS?
3. Что такое preflight-запрос OPTIONS и когда браузер его отправляет?
4. Что такое XSS? Почему строка `<img src=x onerror=alert(1)>` не выполнилась на странице?
5. Что такое CSRF? Почему он опасен для входа через cookie и не опасен для токена в заголовке?
6. Что делают флаги cookie `HttpOnly`, `Secure` и `SameSite`?
7. Где на странице хранится токен? Какие риски у `localStorage` и у cookie?
8. Что такое Content-Security-Policy и от чего она защищает?
9. Зачем проверять данные на сервере, если форма уже проверяет их в браузере?
10. Что видно во вкладке Network: где заголовки запроса и ответа, статус, время?
11. Что будет, если сервер не ответил? Как это обработано на странице?
12. Как сервер может сам отправить данные в браузер? Чем WebSocket и SSE отличаются от обычных запросов?
13. Чем SPA отличается от страниц, которые собирает сервер?

Возможные живые правки: добавить поле в форму; поменять текст ошибки; добавить сортировку списка; показывать на странице число записей.
