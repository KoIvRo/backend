# Лаба 3. Пользователи и доступ

**Цель:** у сервиса появляются пользователи. Читать данные может кто угодно, изменять только тот, кто вошёл, а чужие записи нельзя менять никому, кроме администратора.

Срок: PR из `lab-3` в `main` до 23:59 накануне встречи 4.

## Что сделать

1. **Таблица пользователей**: логин (уникальный), хэш пароля, роль. Пароль хранится **только в виде хэша** bcrypt или argon2. Самого пароля в базе нет.
2. **Эндпоинты** `POST /auth/register` (регистрация) и `GET /auth/me` (кто я).
3. **Закрыть изменения**: все `POST`, `PUT`, `PATCH`, `DELETE` требуют авторизации через Basic Auth. Клиент присылает заголовок `Authorization: Basic <base64 от "логин:пароль">`.
4. **Автор записи**: у каждой записи есть `owner_id`. Его ставит сервер по тому, кто вошёл, а не берёт из тела запроса.
5. **Права**: изменить или удалить запись может только её автор. Чужая запись даёт **403**.
6. **Проверка доступа в одном месте**: middleware, dependency или фильтр, а не копия кода в каждом обработчике.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | `POST /auth/register` создаёт пользователя, повтор с тем же логином даёт 409 | Новый логин даёт 2xx, тот же ещё раз даёт 409 |
| 2 | Пароли хранятся хэшем bcrypt или argon2 | Вручную: чекер печатает логин, в консоли базы делается `SELECT`, значение начинается с `$2b$` или `$argon2id$` |
| 3 | Изменения без авторизации дают 401, с Basic работают; неверный пароль даёт 401 без подсказки | POST, PATCH, PUT, DELETE (и POST связанной записи) без заголовка дают 401. Неверный пароль и несуществующий логин дают 401 с одинаковым телом |
| 4 | `GET /auth/me` возвращает текущего пользователя без пароля и хэша | 200, логин есть, полей `password` и `hash` и значений вида `$2b$...` нет; без авторизации 401 |
| 5 | Запись привязана к автору, `owner_id` ставит сервер | Чекер присылает в теле `"owner_id": 999999`, а в ответе должен быть id из `/auth/me` |
| 6 | Чужую запись изменить и удалить нельзя: 403 | Пользователь B меняет и удаляет запись пользователя A и получает 403; A меняет свою запись; читать чужую можно |

## ★ (2 балла): JWT

- `POST /auth/login` возвращает `{"access_token": "..."}`. Запросы с заголовком `Authorization: Bearer <токен>` работают.
- Подделанный токен (изменённая подпись, подменённый payload, `"alg": "none"`) даёт 401. Просроченный токен тоже даёт 401.
- Секрет и время жизни токена берутся из переменных окружения.

Чекер подделывает токен тремя способами. Просрочку он проверит сам, если запустить сервис со временем жизни токена до 10 секунд. Иначе на приёме нужно показать, откуда берётся срок жизни. Без рабочего входа 0 баллов, всё работает 2, частично 1.

## ★★ (2 балла): администратор и лимит попыток, или вход через GitHub

Один из двух вариантов.

**(а) Администратор и лимит попыток.** Роли `user` и `admin`. Админ может изменять и удалять любые записи. Админ создаётся сидом или из переменных окружения, через регистрацию админом стать нельзя, даже если прислать `"role": "admin"`. После 5 неудачных попыток входа за минуту сервер отвечает **429**. Обе части вместе дают 2 балла, одна даёт 1.

**(б) Вход через GitHub по OAuth 2.0.** Кнопка «Войти через GitHub». `GET /auth/github` перенаправляет на страницу GitHub с `client_id`, `redirect_uri` и `state`. GitHub возвращает пользователя на `/auth/github/callback` с кодом, сервер меняет код на токен GitHub, узнаёт логин, создаёт или находит пользователя и выдаёт свой токен. Приложение регистрируется в GitHub: Settings, Developer settings, OAuth Apps. `client_secret` лежит только в `.env`.

Чекер: для (а) пользователь B получает 403, админ из `contract.auth.admin` получает 2xx, шестая неверная попытка входа получает 429. Для (б) проверяет редирект с `oauth_path`, весь вход показывается на приёме.

## contract.json: что добавить

```json
{
  "auth": {
    "scheme": "basic",
    "register_path": "/auth/register",
    "login_path": "/auth/login",
    "me_path": "/auth/me",
    "login_field": "username",
    "password_field": "password",
    "token_field": "access_token",
    "owner_field": "owner_id",
    "admin": { "username": "admin", "password": "admin-test-pass" },
    "oauth_path": null
  }
}
```

Если при регистрации нужны ещё поля (например, email), добавляется `"register_extra": {"email": "bc@example.com"}`. Если Basic не делался и сразу сделан JWT, пишется `"scheme": "bearer"`. Для варианта (б) в `oauth_path` пишется адрес, с которого начинается вход, например `"/auth/github"`.

С этого момента чекер сам регистрирует тестовых пользователей и отправляет все запросы лаб 1 и 2 с авторизацией.

## Сценарий демонстрации на паре

Регистрация, повторная регистрация (409), POST без авторизации (401), POST с Basic (201), `/auth/me`, хэш в базе, неверный пароль (401), попытка изменить чужую запись (403).

## Подсказки по стекам

| Язык | Хэш | JWT | OAuth |
| --- | --- | --- | --- |
| Python | `bcrypt` | `PyJWT` | `authlib` или запросы через `httpx` |
| JS/TS | `bcrypt` или `argon2` | `jsonwebtoken` | `passport-github2` |
| Go | `golang.org/x/crypto/bcrypt` | `github.com/golang-jwt/jwt/v5` | `golang.org/x/oauth2/github` |
| Java | Spring Security `BCryptPasswordEncoder` | `jjwt` | `spring-boot-starter-oauth2-client` |
| C# | `BCrypt.Net-Next` | `Microsoft.AspNetCore.Authentication.JwtBearer` | `AspNet.Security.OAuth.GitHub` |
| PHP | `password_hash()` | `firebase/php-jwt` | Laravel Socialite |

Лимит попыток проще всего хранить в памяти: словарь «логин: время неудачных попыток». Если копий сервиса несколько, такой счётчик держат в Redis.
