# Лаба 3. Авторизация

**Цель:** у сервиса появляются пользователи. Читать данные может кто угодно, а изменять только тот, кто вошёл.

Срок: PR из `lab-3` в `main` до 23:59 накануне встречи 4.

## Что сделать

1. **Таблица пользователей**: логин (уникальный), хэш пароля, роль. Пароль хранится **только в виде хэша** bcrypt или argon2. Самого пароля в базе нет.
2. **Эндпоинты** `POST /auth/register` (регистрация) и `GET /auth/me` (кто я).
3. **Закрыть изменения**: все `POST`, `PUT`, `PATCH`, `DELETE` требуют авторизации через Basic Auth. Клиент присылает заголовок `Authorization: Basic <base64 от "логин:пароль">`.
4. **Автор записи**: у каждой записи есть `owner_id`. Его ставит сервер по тому, кто вошёл, а не берёт из тела запроса.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | `POST /auth/register` создаёт пользователя, повтор с тем же логином даёт 409 | Новый логин даёт 2xx, тот же ещё раз даёт 409 |
| 2 | Пароли хранятся хэшем bcrypt или argon2 | Вручную: чекер печатает логин, в консоли базы делается `SELECT`, значение начинается с `$2b$` или `$argon2id$` |
| 3 | Все изменяющие запросы без авторизации дают 401, с правильным Basic работают | POST, PATCH, PUT, DELETE (и POST связанной записи) без заголовка дают 401 каждый, с Basic дают 2xx |
| 4 | Неверный пароль даёт 401, и ответ не подсказывает, что именно неверно | Неверный пароль и несуществующий логин дают 401 с одинаковым телом ответа |
| 5 | `GET /auth/me` возвращает текущего пользователя без пароля и хэша | 200, логин есть, полей `password` и `hash` и значений вида `$2b$...` нет; без авторизации 401 |
| 6 | Запись привязана к автору, `owner_id` ставит сервер | Чекер присылает в теле `"owner_id": 999999`, а в ответе должен быть id из `/auth/me` |

## ★ (2 балла): JWT

- `POST /auth/login` возвращает `{"access_token": "..."}`. Запросы с заголовком `Authorization: Bearer <токен>` работают.
- Подделанный токен (изменённая подпись, подменённый payload, `"alg": "none"`) даёт 401. Просроченный токен тоже даёт 401.
- Секрет и время жизни токена берутся из переменных окружения.

Чекер подделывает токен тремя способами. Просрочку он проверит сам, если запустить сервис со временем жизни токена до 10 секунд. Иначе на приёме нужно показать, откуда берётся срок жизни. Без рабочего входа 0 баллов, всё работает 2, частично 1.

## ★★ (2 балла): роли и лимит попыток

- Роли `user` и `admin`. Изменить или удалить чужую запись нельзя, это **403**. Админ может всё. Админ создаётся сидом или из переменных окружения, через регистрацию админом стать нельзя.
- После 5 неудачных попыток входа за минуту сервер отвечает **429**.

Чекер: пользователь B пытается изменить запись пользователя A и получает 403; админ из `contract.auth.admin` получает 2xx; шестая неверная попытка входа получает 429.

## contract.json: что добавить

```json
{
  "auth": {
    "scheme": "basic",
    "register_path": "/auth/register",
    "login_path": "/auth/login",
    "me_path": "/auth/me",
    "login_field": "username",
    "password_field": "password",
    "token_field": "access_token",
    "owner_field": "owner_id",
    "admin": { "username": "admin", "password": "admin-test-pass" }
  }
}
```

Если при регистрации нужны ещё поля (например, email), добавляется `"register_extra": {"email": "bc@example.com"}`. Если Basic не делался и сразу сделан JWT, пишется `"scheme": "bearer"`.

С этого момента чекер сам регистрирует тестовых пользователей и отправляет все запросы лаб 1 и 2 с авторизацией.

## Сценарий демонстрации на паре

Регистрация, повторная регистрация (409), POST без авторизации (401), POST с Basic (201), `/auth/me`, хэш в базе, неверный пароль (401).

## Подсказки по стекам

| Язык | Хэш | JWT |
| --- | --- | --- |
| Python | `bcrypt` | `PyJWT` |
| JS/TS | `bcrypt` или `argon2` | `jsonwebtoken` |
| Go | `golang.org/x/crypto/bcrypt` | `github.com/golang-jwt/jwt/v5` |
| Java | Spring Security `BCryptPasswordEncoder` | `jjwt` |
| C# | `BCrypt.Net-Next` | `Microsoft.AspNetCore.Authentication.JwtBearer` |
| PHP | `password_hash()` | `firebase/php-jwt` |

Проверка авторизации делается в одном месте (middleware, dependency или фильтр), а не копируется в каждый обработчик.
