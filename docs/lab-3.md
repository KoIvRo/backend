# Лаба 3. Авторизация

**Цель:** у сервиса появляются пользователи, изменять данные могут только вошедшие.

Срок: PR `lab-3 → main` до 23:59 накануне встречи 4.

## Что сделать

1. Таблица пользователей: логин (уникальный), хэш пароля, роль. Пароль хранится **только хэшем** bcrypt или argon2.
2. `POST /auth/register` и `GET /auth/me`.
3. Все изменяющие запросы (`POST`, `PUT`, `PATCH`, `DELETE`) требуют авторизации — Basic Auth: заголовок `Authorization: Basic base64(логин:пароль)`.
4. У каждой записи — автор (`owner_id`), его ставит сервер из авторизации.

## Чек-лист базы (6 баллов) и как его проверяет чекер

| № | Пункт | Как проверяется |
| --- | --- | --- |
| 1 | `POST /auth/register` создаёт пользователя; повтор с тем же логином → 409 | Свежий логин → 2xx, тот же ещё раз → 409 |
| 2 | Пароли хранятся хэшем (bcrypt или argon2) — показать строку в БД | **Глазами:** чекер печатает логин, ты делаешь `SELECT` в консоли БД — значение начинается с `$2b$` или `$argon2id$` |
| 3 | Все изменяющие запросы без авторизации → 401; с правильным Basic → работают | POST, PATCH, PUT, DELETE (и POST ребёнка) без заголовка → 401 каждый; с Basic → 2xx |
| 4 | Неверный пароль → 401, ответ не подсказывает, что неверно | Неверный пароль и несуществующий логин → 401, тела ответов одинаковые |
| 5 | `GET /auth/me` — текущий пользователь без пароля и хэша | 200, есть логин, нет полей `password`/`hash` и значений вида `$2b$...`; без авторизации → 401 |
| 6 | Запись привязана к автору, сервер ставит `owner_id` сам | Чекер шлёт `"owner_id": 999999` в теле — в ответе должен быть id из `/auth/me` |

## ★ (2 балла): JWT

- `POST /auth/login` → `{"access_token": "..."}`; запросы с `Authorization: Bearer <токен>` работают.
- Подделанный токен (изменённая подпись, подменённый payload, `"alg": "none"`) → 401. Просроченный → 401.
- Секрет и время жизни — из переменных окружения.

Чекер подделывает токен тремя способами. Просрочку он проверит сам, если запустить сервис со сроком жизни ≤ 10 секунд; иначе покажешь глазами, откуда берётся срок. Без рабочего входа — 0; всё остальное работает — 2; иначе 1.

## ★★ (2 балла): роли и лимит попыток

- Роли `user` / `admin`: изменить или удалить чужую запись → **403**, админ может всё. Админа создавай сидом или из переменных окружения — регистрацией стать админом нельзя.
- После 5 неудачных входов за минуту → **429**.

Чекер: пользователь B трогает запись A → 403; админ из `contract.auth.admin` → 2xx; шестая неверная попытка входа → 429.

## contract.json: что добавить

```json
{
  "auth": {
    "scheme": "basic",
    "register_path": "/auth/register",
    "login_path": "/auth/login",
    "me_path": "/auth/me",
    "login_field": "username",
    "password_field": "password",
    "token_field": "access_token",
    "owner_field": "owner_id",
    "admin": { "username": "admin", "password": "admin-test-pass" }
  }
}
```

Если при регистрации нужны ещё поля (например, email), добавь `"register_extra": {"email": "bc@example.com"}`. Если Basic не делал и сразу сделал JWT — `"scheme": "bearer"`.

С этого момента чекер сам регистрирует тестовых пользователей и шлёт все запросы лаб 1–2 с авторизацией.

## Сценарий демонстрации на паре

Регистрация → повторная регистрация (409) → POST без авторизации (401) → POST с Basic (201) → `/auth/me` → хэш в БД → неверный пароль (401).

## Подсказки по стекам

| Язык | Хэш | JWT |
| --- | --- | --- |
| Python | `bcrypt` | `PyJWT` |
| JS/TS | `bcrypt` / `argon2` | `jsonwebtoken` |
| Go | `golang.org/x/crypto/bcrypt` | `github.com/golang-jwt/jwt/v5` |
| Java | Spring Security `BCryptPasswordEncoder` | `jjwt` |
| C# | `BCrypt.Net-Next` | `Microsoft.AspNetCore.Authentication.JwtBearer` |
| PHP | `password_hash()` | `firebase/php-jwt` |

Проверку авторизации делай в одном месте — middleware, dependency или фильтр, — а не копируй в каждый обработчик.
