# Курс «Backend-разработка»: как всё устроено

За семестр ты собираешь **один проект** по своей теме: HTTP-сервис → база данных → авторизация → веб-клиент → Docker. Каждая лаба добавляет новый слой к тому же репозиторию, а на последней встрече ты защищаешь проект как продукт.

| Лаба | Что добавляется | Задание |
| --- | --- | --- |
| 1 | HTTP-сервис, CRUD в памяти | [lab-1.md](lab-1.md) |
| 2 | Реляционная БД, вторая сущность, миграции | [lab-2.md](lab-2.md) |
| 3 | Пользователи, пароли, авторизация | [lab-3.md](lab-3.md) |
| 4 | Веб-клиент, который работает с API | [lab-4.md](lab-4.md) |
| 5 | Docker и запуск одной командой | [lab-5.md](lab-5.md) |

Темы — в [themes.md](themes.md). Язык бэкенда любой: Python, JS/TS, Go, Java, C#, PHP. Проверяется поведение API, а не код.

## Баллы

| Компонент | Максимум |
| --- | --- |
| Посещение | 8 (по 1 за встречу) |
| Лабы | 60 (5 × 12: база 8 + ★ 2 + ★★ 2) |
| «Своя игра» | 10 |
| Защита | 22 |

Оценка: 86–100 — 5, 76–85 — 4, 61–75 — 3. Без звёздочек максимум 80 баллов, то есть «4».

**Одна лаба — 12 баллов:** 6 пунктов чек-листа по 1 баллу, вопрос на понимание до 2 баллов, ★ до 2, ★★ до 2. Лаба **принята**, если в чек-листе ≥ 4 пунктов из 6 и ты объяснил свой код. Звёздочки смотрят только у принятой лабы.

## Как сдавать

1. Для каждой лабы — ветка `lab-1` … `lab-5` от `main`.
2. Пока делаешь — гоняй чекер: `backcheck --lab N --stars`. Установка и все флаги — в [README чекера](https://github.com/bozhedom/backcheck).
3. Готово → `backcheck --lab N --stars --report` и открой **Pull Request** `lab-N → main`. В описании отметь чек-лист и вставь содержимое `backcheck-report.md`.
4. На паре: запускаешь сервис, прогоняешь чекер, отвечаешь на вопрос, иногда вносишь маленькую правку в код. После приёма PR вливается в `main`.

```bash
git switch main && git pull
git switch -c lab-2
# ... работа ...
git add . && git commit -m "Лаба 2: PostgreSQL, вторая сущность"
git push -u origin lab-2
# дальше — кнопка «Compare & pull request» на GitHub
```

## Сроки

- **Дедлайн** — открытый PR до 23:59 накануне встречи, на которой лабу принимают. В 23:59 записывается, какой коммит был в PR: если допишешь ночью, сдавать придётся как опоздание.
- **Не успели принять на паре** из-за очереди — принимается в начале следующей встречи без потерь.
- **PR позже срока** или **повторная сдача** после «не принята» — только база (до 8 баллов).
- **Крайний срок любых долгов** — встреча 7.
- **Допуск к защите** — приняты базы лаб 1–3.

## Что происходит на приёме (3–4 минуты)

1. На экране твой PR и README.
2. Ты запускаешь сервис и `backcheck --lab N -i`. Пункты, которые не видны по HTTP, преподаватель смотрит глазами.
3. Вопрос из списка в задании лабы: 2 балла — ответил сам и показал в своём коде, 1 — с подсказкой.
4. Иногда — **живая правка** на 2 минуты: «добавь поле», «поменяй код ответа». Можно IDE и документацию, нельзя ИИ-ассистента.

**ИИ разрешён, списанное — нет.** Пиши код с чем угодно, но сдаёт тот, кто понимает свой код. Не объяснил или не смог внести простую правку — лаба не принята на этой встрече.

## Договорённости, о которых часто спорят

| Ситуация | Как считается |
| --- | --- |
| FastAPI отдаёт 422 вместо 400 на неправильное тело | В базе засчитывается. В ★ (единый формат ошибок) нужен именно 400 |
| `DELETE` отдаёт 200 с телом | Не засчитывается: нужен 204 |
| id — UUID | Нормально, укажи несуществующий UUID в `missing_id` |
| Список в обёртке `{"items": [...]}` | Нормально, укажи `"list_key": "items"` |
| Сразу сделал JWT без Basic | База лабы 3 засчитывается через Bearer (`"scheme": "bearer"`) |
| SQLite вместо PostgreSQL | Можно; в лабе 5 файл БД должен лежать в volume |
| Сервис не запустился на паре | Не принята на этой встрече, но не опоздание: сдаёшь на следующей |
